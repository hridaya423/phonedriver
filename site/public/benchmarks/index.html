phonedriver benchmarks: speed, tokens and real phone jobs

phonedriver reads a 1,000-row list in 24.0 ms where adb takes 2,352.4 ms: 98 times faster at p50 (95% CI on the ratio 92.2 to 106.0). The rest of this page is every operation we timed, what the agent spent in tokens, and the part we have not run yet.

Speed against adb and phone-harness

p50 of 50 runs after 20 warm-ups, on an Android 17 emulator (API 37, headless, software rendering). Everything ran on the emulator's own host with the three tools interleaved. Mean host CPU load was 13% to 39% per operation from other work on the machine. Bars are drawn to scale within each operation; the tick is p95.

How to read it

  • The bare tap is the closest row. Host to reply, phonedriver takes 175.6 ms when taps come back to back (1.1 times faster than adb) and 61.6 ms when they are 1.5 s apart (1.7 times). Measured on the device, from the host sending a tap to the testbed's touch listener logging it, it is 27.5 ms against adb's 71.2 ms and phone-harness's 76.6 ms (clock offset good to about 8 ms).
  • Our tap misses its own 15 ms budget (decision D14), and typing 100 characters misses its 150 ms budget (251.1 ms).
  • adb returns raw XML and a tap that returns before the app reacts. phonedriver returns a pruned, numbered tree and waits for the app. Different outputs for the same job. For "tap, then what changed", the adb row is a tap, one uiautomator dump and a diff in the caller.
  • adb input text and phone-harness cannot type Unicode. phonedriver typed 100 mixed-script characters (ASCII, accents, CJK, Arabic, emoji) in 225.0 ms.
  • Fresh daemon to first screen read: phonedriver 1,620.5 ms, phone-harness 2,999.4 ms (new Python process), adb 2,488.0 ms (one dump; adb has no cold start, so this is for scale only).
  • phone-harness's helpers ran in process, which spares it a Python start per call and favours it.
  • Emulator only. No physical Android phone and no iOS device is in this run. On the iOS 26.5 Simulator a tap takes 357 ms against 80 ms for the Simulator's own tool, because XCTest takes about 240 ms to confirm the event (D15). On an iPhone 14 Plus and an iPad Pro (M5) it takes 534 and 454 ms.

The earlier 153x figure came from a quieter, single-tool run and is not current. The full method, machine state and the history of the number are in the repo.

Tokens: what an agent spends on a task

Claude Sonnet 5.5 through claude -p, each harness the only tool, three tasks checked from device state (the alarm database, the testbed event log, the answer text), never from the agent's claim. Tokens are input, output, cache creation and cache read. Device: a 2560x1600 tablet emulator.

Task (checked from device state)phonedriver, 2 to 3 runs, median tokensphone-harness, 3 runs, median tokens
alarm-gym: 7:30 AM weekday alarm "Gym" in Clock110,419 (19.5 calls)220,723 (19 calls)
wiki-birthdate: Chrome, Wikipedia, Grace Hopper's birth date57,753 (7 calls)53,403 (7 calls)
testbed-web-form: fill and submit a web form50,185 (7 calls)56,249 (6 calls)
Sum of the three medians218,357330,375

On the sum of medians phonedriver used 34% fewer tokens than phone-harness (218,357 against 330,375). It is ahead on the longest task, level on the form and 8% behind on the Wikipedia task, where individual runs ranged from 26,147 to 64,522 tokens. These are 2 to 3 runs per cell: they show what happened, not a rate. Raw adb finished alarm-gym in 2 calls with a SET_ALARM intent (18,607 tokens), a shortcut the task allows, and failed the web form, a WebView with no accessibility nodes.

mobile-mcp is not compared here. It failed all runs in this setup ("device server did not start within 5s", plus an adb forward bind error against a remote adb server). That is a fault of the setup, not a measured capability, and its token totals are the cost of retrying a broken tool. It needs a run on a local emulator or phone.

The fixed cost per turn is also measured: the first turn of a one-word claude -p costs 5,606 tokens with phonedriver's 14 MCP tools and 5,214 with phone-harness. All three rounds, the fixes between them and the caveats.

Real phone jobs

Nine jobs only a phone can do: the result cannot be produced by adb, am, cmd, settings, content or a web search. Each is checked from device state by a script, not by the agent's say-so. The checks are built and proven by hand on an emulator. Agent runs have not finished. The results column fills in when they do.
