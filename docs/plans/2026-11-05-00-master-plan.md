# phone-use Master Plan

> **For Claude:** REQUIRED SUB-SKILL: Use `executing-plans` to implement phase by phase, task by task. Read `AGENTS.md` first.

**Goal:** Ship phone-use, the fastest and most exact way for an AI agent to see and operate Android and iOS devices, and prove it with numbers against phone-harness.

**Architecture:** One Rust binary (CLI, daemon, MCP). The daemon keeps a persistent connection per device: a shell-uid Java agent on Android; CoreDevice services and an XCTest runner on iOS. A pure core turns raw trees into stable refs, rendered snapshots, diffs, and settle decisions. Details in `docs/architecture.md`.

**Tech Stack:** Rust (tokio, serde, interprocess, rmcp, openh264, idevice, proptest, insta), Java 17 source compiled with `javac` + `d8` for the Android agent, Objective-C XCTest for the iOS runner, XcodeGen, Gradle (Android testbed only).

## Spikes are throwaway

Phase 1 and the iOS spikes in Phases 5 and 6 live in `spikes/<name>/` and are deleted at the end of their phase. Their value is the numbers and the "it works on API N" facts, recorded in `docs/spikes/`. Production code is written fresh against the architecture with tests.

## How each task is written

Every task lists exact files, the failing test first, the command that shows it failing, the implementation approach, and the command that shows it passing. Tests prove behavior through real boundaries:
- `core`: pure unit, property (`proptest`), and golden (`insta`) tests. No mocks needed.
- Device code: integration tests against the emulator or simulator, gated with `#[ignore]` plus the env var `PHONE_USE_TEST_DEVICE`. They run in the dev loop and in a manual CI job, not on every push.
- End to end: the testbed apps log every touch, key and text change with timestamps. Tests compare what the testbed received with what was sent. This is the ground truth; a test that only checks our own reply is not enough.

## Verification standard

From the user's `AGENTS.md`: evidence means something observed this session. For every task, record in `progress.md` the command run and the output that proved it. For anything visual (snapshot rendering, screenshots), look at the image. A latency claim needs a `bench` run with p50 and p95.

## One-way doors in this project (stop and ask)

- Driving any physical phone or tablet. Name the device and what will happen.
- Installing anything on a physical device (the runner, profiles).
- Downloading DDI images on a machine without Xcode.
- Creating a GitHub repository, pushing, publishing crates, Homebrew, npm, or PyPI.
- Choosing the license (decision D13).
