## Fixes made for this result

- The shade kick (hollow-tree repair) waited a fixed 600 ms between expanding and collapsing the notification shade; a collapse sent while System UI was stalled was lost and the shade stayed open over every later scenario. It now waits until a system window holds input focus (the open shade), collapses, and waits until it is gone. Red test `the_shade_kick_leaves_the_shade_closed_when_system_ui_stalls` (System UI stopped with `kill -STOP` for 1.5 s): red 2 of 2 with the old code, green 3 of 3 on API 37 and green on API 26. A first version that treated any large system window as the shade collapsed too early on Settings' first start and left the shade open in about 3 of 4 `settings-search` runs; the focus test fixed it (6 of 6).
- `paste` (the default `type` mode) pasted into a field that had not taken focus yet and answered ok (`settings-search`, about 3 failures in 100 runs on API 37). The agent now waits up to 1.5 s for a focused input before pasting. Red test `paste_waits_for_a_field_that_takes_focus_late` (testbed tab `latefocus`, focus after 700 ms), green 3 of 3.
- `scroll --until` reported `settled` even when the last scroll's settle had timed out. It now reports the last settle. Daemon test `scroll_until_reports_unsettled_when_the_last_scroll_never_settled`, red then green.

## API 37 emulator: what the evidence says now

The earlier agent's trials (`D:/pu-m2/trials/trials.tsv` on win-pc) showed hangs and deaths with lavapipe (a launch without `-gpu swangle_indirect`) and none in 11 trials with it. In this session two emulators launched with `-gpu swangle_indirect` (the log says `Selecting Vulkan device: SwiftShader Device`) still stopped: one died silently while `chrome-open-page` ran, another hung (adb shell silent, crashpad_handler crash in the Application log) during `settings-search` runs, and a third run of the same kind completed. Another session's emulator `Baton_API_37` was running on the same PC the whole time. So swangle removes the reproducible WebView crash but is not shown to make the emulator stable, and a second emulator on the PC remains a suspect that was not tested. The suite figure above is from an emulator that was up for the whole three-run invocation.

## Environment findings

- The win-pc emulators died or hung 6 times in about 12 hours; five of the six coincide with the first use of a WebView (Chrome, or the testbed's web tab). The stock-app scenario that used Chrome (`chrome-open-page`, first-run screens dismissed, page text `Example Domain` asserted) passed on API 37 in 2 of 2 and killed the emulator in the third run; it was moved to `bench/scenarios/android-unstable/` and replaced by `settings-battery`.
- Two emulators running at the same time coincided with the deaths; the API 26 final runs were made with the API 37 emulator stopped.
- A fresh cold boot of the API 37 image needs several minutes before `System UI` answers.
