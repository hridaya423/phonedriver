## Verdict

phone-use is faster than adb and phone-harness on every operation measured here. The ratio against adb runs from 1.1x (a tap sent back to back with others) to 98x (reading a 1,000-row list). Against phone-harness it runs from 1.3x to 111x. The headline "up to 98x faster than adb" is the list read: 24.0 ms against 2,352.4 ms at p50, 95% CI on the ratio 92.2 to 106.0.

The bare tap is the weak row. Host to reply it is 175.6 ms when taps come back to back and 61.6 ms when they are 1.5 s apart, as an agent sends them. Measured on the device, from the host sending the tap to the testbed's touch listener logging it, phone-use is 2.6x faster than adb (27.5 ms against 71.2 ms).

## What happened to the 153x

The first run (`docs/bench/m1.md`) read the 1,000-row list in 15.5 ms against phone-harness's 2,370 ms, a ratio of 153. The later busy-machine run (`docs/bench/adb.md`) used a different baseline and a different load, and its chart showed 51x against adb with a tap that looked slower than phone-harness's. This run holds the three tools to one machine state and interleaves them. The list read is 24.0 ms against 2,653.7 ms (111x phone-harness, 98x adb). phone-use's list read is 8 ms slower than in M1 and phone-harness's is 280 ms slower, so the ratio is lower than 153 on both counts. The 153 is not a current number and is not used anywhere.

## Method

`bench/speed/run_speed.py` runs every tool in one process on the host.

- **Interleaved.** Taps, screenshots, typing and the device-side tap alternate tool by tool, sample by sample, with the start order rotating. The three tools that read the UI tree cannot run at once, because phone-use's on-device agent holds the one UiAutomation connection that `uiautomator dump` needs (adb and phone-harness fail with "Killed" while it is up). For those ops (both tree reads and tap then what changed) the tools take turns in 5 round-robin blocks of 10 samples, and the phone-use daemon and agent are stopped while the others run.
- **Warm-up.** 20 runs per tool and op, discarded. Later blocks discard 3.
- **Samples.** 50 per tool and op, plus 50 for phone-use's settled snapshot and for its mixed-Unicode typing.
- **Statistics.** p50 and p95 per tool. The interval on each p50 ratio is a bootstrap 95% CI: each tool's samples resampled alone, 10,000 times, seed 7 (`bench/speed/stats.py`).
- **Headline rule.** A row's headline ratio is its p50 ratio, unless the lower bound of its interval is below 90% of the p50 ratio, in which case the lower bound is the headline. The list read's bound (92.2) is above 88.3, so its headline is the p50 ratio, 98x. Rows in the chart show p50 ratios.
- **Operations.** As in M1 and `docs/bench/adb.md`: tap at a point on the Taps tab (adb and phone-harness at the same pixel); screenshot to a file; tree read of the Settings main screen and of the List tab (phone-use `snapshot --no-settle`; its settled snapshot is in the table); 100 ASCII characters typed into a text field (the same text for all three); tap on the Dark theme switch and learn what changed (adb: tap, one `uiautomator dump`, diff of node tuples, as in `docs/bench/adb.md`). phone-harness has no settle or diff, so that row has no phone-harness bar.
- **Device-side tap.** The Gestures tab logs each `ACTION_DOWN` to logcat (`adb logcat -v epoch`). Latency is the logged time minus the host's send time, with the emulator's clock offset measured through a persistent `adb shell` (offset 0.8122 s before, 0.8126 s after; round trip 15 ms, so each figure is good to about 8 ms). It does not use any reply from phone-use.

## Cold start

From a stopped daemon to the first screen read, 10 rounds, alternating tools (second pass): phone-use 1,620.5 ms (`daemon stop`, then one CLI `snapshot`, which starts the daemon, finds the agent jar on the device and boots the agent), phone-harness 2,999.4 ms (a fresh Python process, import, first `screen()`), adb 2,488.0 ms (one `uiautomator dump` against the already running adb server). adb has no cold start of its own, so its figure is the same call as the Settings tree row; the comparison is for scale, not a like-for-like. First pass: 1,807.8, 3,232.4 and 2,556.7 ms.

## What this does not show

- Taps. When taps follow each other with no pause, phone-use's reply takes 175.6 ms here, not the 30 to 37 ms of M1, and its lead over adb is 1.1x. A short diagnostic run, not in the CSV (35 timed taps each, phone-use alone), gave p50 179.7 ms back to back, 127.8 ms with 0.5 s between taps, and 56.7 ms with 1.5 s between. The paced row was added after that diagnostic. Both rows are in the chart. The device-side row is the one that does not depend on phone-use's own reply.
- Host load was 10% to 47% during the first pass, from other work on the host. Typing, the one op measured at two load levels, gave close ratios against adb in both passes (20.4x at 32% load, 19.3x at 20%), and absolute times move with load (phone-harness's 100-character typing took 2,104.5 ms in M1 and 5,523.3 ms here; adb's 4,840.9 ms is in line with `docs/bench/adb.md`). Absolute numbers are for this host.
- Emulator only. No physical Android phone and no iOS device are in this run.
- adb returns raw XML and a tap that returns before the app reacts. phone-use returns a pruned, numbered tree and waits for the app. Different outputs, same job for an agent.
