# M1 benchmark: phone-use against phone-harness 0.3.3 on Android

Task 2.10, milestone M1. Everything below was measured on win-pc, next to the emulator, with the default local adb server (architecture section 12 says why the SSH tunnel is not used for budgets). Raw samples are in `docs/bench/data/`.

## Verdict

**M1 is met.** phone-use is faster than phone-harness on every operation phone-harness supports, by 3x to 150x at p50, and the slowest sample of every such op in both phone-use runs is below phone-harness's p50 for it (tap: 91.5 ms against 110.7 ms).

**Three of the five Android budgets of architecture section 12 are met and two are missed.** Met: snapshot (Settings main, `--no-settle`), screenshot, tap to settled diff. Missed: `tap` (p50 29.7 and 36.5 ms against 15 ms) and `type 100 chars` (253 and 288 ms against 150 ms). Two other misses (snapshot 88 ms, screenshot 36 ms) were profiled, fixed and re-measured in this task; the remaining two are explained per row below as limits of the emulator and of design choices recorded in architecture 6.2, not host code. No budget was relaxed and no measurement was tuned.

## phone-harness 0.3.3 (50 runs after 5 warm-ups)

Command (`bench/baseline/run_baseline.py`, launched detached because an ssh session ends it):

```
$env:DO_NOT_TRACK="1"; $env:PHONE_HARNESS_TELEMETRY="0"; $env:PHONE_HARNESS_NO_UPDATE_CHECK="1"
$env:PHONE_HARNESS_PLATFORM="android"; $env:ANDROID_SERIAL="emulator-5554"
.\ph\Scripts\python.exe run_baseline.py --runs 50 --warmup 5 --unicode-check --csv baseline.csv
```

The helpers are called in process (`from phone_harness import helpers`), which is the best case for phone-harness: an agent running `phone-harness -c ...` per call also pays a Python start.

| op | p50 ms | p95 ms | max ms | what limits it |
|---|---|---|---|---|
| `tap(x, y)` | 110.7 | 140.7 | 255.3 | one `adb shell input tap` process per call (about 75 to 90 ms), plus two `dumpsys` reads every 2 s for its lock and wakefulness gate, which is why p95 is higher |
| `screenshot()` | 390.1 | 425.3 | 435.1 | `adb exec-out screencap -p` (a full-size PNG, 1080x2424, encoded on the device and piped) and a process start |
| `screen()`, Settings main | 2426.4 | 2467.0 | 2475.7 | `adb exec-out uiautomator dump`, which waits for the UI to go idle; also one `dumpsys window displays` |
| `screen()`, List tab | 2370.0 | 2401.2 | 2419.2 | same |
| `type_text` 100 ASCII chars | 2104.5 | 2317.7 | 2466.8 | `adb shell input text`, about 20 ms per character on this device |
| tap to settled diff | unsupported | | | no settle and no diff; it has `wait_stable`, which is not the same operation |

**Unicode.** `type_text("héllo 世界 مرحبا 👋🏽 abc 123 ")` raises `RuntimeError: adb shell input text '...' failed: ... java.lang.NullPointerException: Attempt to get length of null array`, and the field stays empty. phone-harness cannot type Unicode through `input text`; phone-use pastes it exactly (`type_enters_unicode_exactly_and_reports_verified`, and the 100-character row above).

**Telemetry is off and nothing leaves the machine.** Before the timed run, `bench/baseline/outbound_check.ps1` ran the same helpers (`screen`, `tap`, `screenshot`, 15 calls in 12 s) with the variables above:

```
telemetry.is_enabled() = False
network events raised in this process: none        (sys.addaudithook: no socket.connect, no DNS lookup)
distinct connections seen from the python process and its children: (none, polled every 25 ms with Get-NetTCPConnection)
no connection to any address other than loopback
5 x subprocess.Popen adb shell "input tap 300 800", 5 x adb exec-out screencap -p, 5 x adb exec-out uiautomator dump /dev/tty, 6 x dumpsys power, 6 x dumpsys window ..., 10 x dumpsys window displays
```

The Python audit hook is the stronger evidence: it sees every socket connect and name lookup the process makes, including ones too short to poll. `Get-NetTCPConnection` could not see the short-lived `adb` children's loopback connections either. The helper path never imports the telemetry sender (it lives in `run.py`, the CLI), so the check is mainly that the `DO_NOT_TRACK` family of variables does what the plan assumes.

## What limits each phone-use number

Measured by timing the layers separately: `Control::request` on the host (write to reply), the agent's own `System.nanoTime` around each op (returned in the reply), and, for the screenshot, each stage of `encode_png`. These probes were temporary and are not in the tree.

- **tap, 29.7 and 36.5 ms (budget 15, missed).** From the first 23 point taps of a profiled run: host request to reply 25.9 ms p50, of which the agent took 18.9 ms and adb transport (server, emulator adbd, back) about 7 ms; the bench-side total was 28.1 ms, so the daemon, the named pipe and JSON cost about 2 ms. The agent's 18.9 ms is `INJECT_INPUT_EVENT_MODE_WAIT_FOR_FINISH` on the last event (architecture 6.2: the reply means the app handled the event), which waits for the testbed's main thread on a software-rendered emulator; with the final event injected `ASYNC` the same op took 5.2 ms in the agent and 15.1 ms p50 end to end. **I did not adopt that**: it still sits on the 15 ms line (it is not a clean win), and it turns "delivered" into "queued", so a `--no-settle` snapshot straight after a tap could read the old screen. The budget stands as a target; the 7 ms of adb transport alone is half of it on an emulator, and USB hardware is not measured until a physical phone is available (Phase 3).
- **snapshot, Settings main, `--no-settle`, 60.1 and 67.7 ms (budget 80, met).** The agent's tree read is about 50 ms of that, all of it `getChild` binder round trips for 155 nodes (`node()` JSON is 1.5 ms). The rest is transport, JSON parse, pruning, ref assignment and rendering on the host (about 8 to 15 ms, not separated). **Changed in this task:** before it, the same read took 83 to 105 ms in the agent (p50 snapshot 88.4 ms, a miss). `getChild(i, FLAG_PREFETCH_DESCENDANTS_DEPTH_FIRST)` is cancelled by the next call unless `FLAG_PREFETCH_UNINTERRUPTIBLE` is also set, so every node past the root's first batch paid its own binder call: 78 to 103 ms in `getChild` against 41 to 46 ms with the flag (settled snapshot p50 84 to 97 ms before, 58 ms after; same 155 nodes). `getChild(i)` with no flag was worse (118 to 137 ms). API 33 and above only; below that the agent is unchanged.
- **snapshot, Settings main, settled, 58.1 and 59.7 ms.** Same tree read; a settled screen has nothing to wait for.
- **snapshot, List tab, 13.4 and 15.5 ms.** The RecyclerView has bound about a dozen rows, so the tree is small (the 1,000 rows are not in it). Scrolling is the only way to read more.
- **screenshot, 15.2 and 13.7 ms (budget 30, met).** The latest decoded frame is scaled, converted and PNG-encoded on the host and written to disk. **Changed in this task:** before it the p50 was 36.0 and 36.9 ms (a miss) because `resample` spent 30 to 55 ms of it in the box filter, which did six integer divisions per output pixel for three planes. It now precomputes the column spans and sums whole rows into a `u32` accumulator, one division per output pixel (`resample_matches_the_per_pixel_box_filter_down_and_up` pins its output to the old per-pixel version, byte for byte, on seven shapes including upscales). Now about 12 ms is resample, YUV to RGB and PNG at `Compression::Fast`, and 1 to 2 ms is the file write. I looked at the PNG it writes (411x923, the Text tab with the keyboard up); it is sharp.
- **tap to settled diff, 544.0 and 419.5 ms (budget 600, met at p50; p95 729 and 766 ms is above it).** Settle waits at least 250 ms after the last significant input, then needs frames to show the screen is quiet; the toggle animates, and a static screen produces about 3 frames per second (spike A3), so the end of the animation is seen up to one frame period late. Not profiled further, since the budget is met. The 125 ms spread between runs is emulator noise, not a code difference.
- **type 100 characters, 253.3 and 288.3 ms (budget 150, missed).** Agent time for a paste, from 14 profiled samples of the same op: `getClip` 1 to 38 ms, reading the focused field 2 to 48 ms (a `clearCache` plus `findFocus` binder call), `setClip` 2 to 45 ms, the `KEYCODE_PASTE` injection with `WAIT_FOR_FINISH` 10 to 200 ms (the app lays out 100 mixed-script characters on a software renderer), then the confirmation that the field's text changed before the clipboard is restored (architecture 6.2, spike A4: restoring at once can paste the old clip), then `setClip` again. About one run in three waited the full 500 ms of that confirmation (11 to 14 polls) because the accessibility text of the Compose field had not changed yet; those are the p95 of about 790 ms. Reducing it means giving up either the clipboard-restored-on-reply guarantee (`paste_types_unicode_exactly_and_restores_the_clipboard`) or the wait that makes Chrome and Compose fields paste the right text, so I left it: the observed cost of the safeguard is the miss. phone-harness types 100 ASCII characters in 2.1 s and cannot type this string at all.
- **tap on a ref, 121.6 and 126.7 ms (no budget).** One tree read to resolve the ref (about 55 ms), the gesture (27 ms) and the host work.

## Windows fixes made in this task

Each was found by running the suite or the CLI on win-pc, and the Mac suite still passes.

1. **The daemon held its caller's pipes open (runtime, process detach).** `phone-use` starts the daemon with `Command` and `DETACHED_PROCESS`, but `CreateProcess` hands the child every inheritable handle of its parent. Run by `ssh`, by `assert_cmd` or by an agent harness that captures output, the first call that auto-started the daemon did not return until the daemon exited fifteen idle minutes later (reproduced: `cli` test binary hung 3 runs of 4; `ssh win-pc 'phone-use devices'` never returned). `crates/cli/src/detach.rs` now creates the daemon with `CreateProcessW` and a `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` naming only `NUL`, the readiness pipe and the log file, in one small `unsafe` module (`std::process::Command` cannot restrict the list on stable Rust; `raw_attribute` is unstable). After it: the `cli` test binary passed 6 of 6 runs and the same `ssh` call returns in 2.6 s with the daemon still running. A test cannot see the missing handles from the Mac; the existing `devices_starts_the_daemon_and_the_next_call_reuses_it` is the regression test on Windows, where it hung without the fix.
2. **Tests used one pipe name for all tests and Unix paths for sockets (tests).** `cli.rs` named the pipe after the process id, so its parallel tests shared one; `daemon.rs` and `e2e.rs` passed `home/d.sock` as the socket, which on Windows is not a pipe name, and waited for it with `Path::exists`. They now derive a per-test pipe name from the temp directory and wait by connecting. `e2e.rs` no longer sets `PHONE_USE_SOCKET` at all, so it uses the real default path.
3. **`adb_fake_server.rs` did not compile on Windows.** It made its fake `adb` with `std::os::unix`. It now writes `adb.cmd` on Windows.

The whole workspace, `cargo test --workspace`, is green on win-pc (86 core, 9 cli, 21 daemon, 9 adb fake server, 12 video, 8 android unit, 3 and 2 others; the device tests are `#[ignore]`d). Device tests also ran from the Mac through the tunnel on API 37 after the agent change (`agent_live` 7 of 8, the failing one `set_and_keys...` fails the same way without the change; `device_live` 5 of 5; `e2e` 10 of 10). On API 26, `set_and_keys...` fails with and without the change, and `tap_gesture_lands_within_one_pixel...` failed in two full runs with the change and passed three times alone; API 26 takes the unchanged code path (the prefetch flags are API 33 and above), so I take that as the existing flakiness of that emulator rather than a result of this change.
