# M3: agent evaluation (task 4.5)

Runner: `bench/agent-eval/run.sh <tuning|heldout> <runs> <out-dir> [task]` (tasks in `bench/agent-eval/tasks.yaml`, checks and resets in the scenario runner's step language, `phonedriver-bench eval ...`). Each run: reset the emulator state, a fresh `PHONEDRIVER_HOME` with `PHONEDRIVER_TRACE_FULL=1`, then `claude -p "<task>" --mcp-config <generated from mcp.json> --strict-mcp-config --allowedTools "mcp__phonedriver__*" --tools "" --disable-slash-commands --setting-sources "" --model claude-sonnet-5-5 --output-format stream-json --verbose` from an empty directory (no CLAUDE.md, no skills, no built-in tools: the agent sees only the ten MCP tools and the server's one-paragraph instructions, not `SKILL.md`), kill the run's daemon, run the programmatic check, run cleanup. Device: `Pixel_API_37` (`emulator-5554`, `-gpu swangle_indirect`) on win-pc with two other emulators present. Tokens are input + output + cache creation + cache read as reported by the result event.

## App availability (checked before any held-out run)

Files (`com.google.android.documentsui`), Chrome (`com.android.chrome`) and Clock (`com.google.android.deskclock`) are installed on the API 37 image. No substitution was needed. The Compose tab of the testbed had one switch; it now has three (`compose_switch`, `_2`, `_3`, left to right) so "the third switch" exists.

This is the second pass at the gate, not the first. The first pass over the held-out set scored 9 of 15 (airplane, Chrome and Compose 9 of 9; Files 0 of 3; Clock 0 of 3). I read all six failing transcripts: in every one the agent did the task and the check was wrong or the device was not reset. Those two tasks were rerun after the fixes below, and every number in the table is from a run made after the fix. I have not hidden the first pass because the checks of two held-out tasks were written without being tried first; they should have been run against a hand-made success before the gate.

| First-pass failure | Transcript | Class | Fix |
|---|---|---|---|
| `files-new-folder` x3 | the agent created `phonedriver` in Downloads (run 1) and later runs saw it exist | check defect: `find /sdcard -name phonedriver` does not follow the `/sdcard` symlink, so it printed nothing | the check and the reset use `/sdcard/` |
| `clock-timer-3min` x3 | the agent set 3 minutes and pressed Start; the screen said `3 minutes remaining` | check defect: it looked for the timer's notification, which Clock does not post while its own screen is in front | the check reads the `TIMER_EXPIRED` alarm: `dumpsys alarm` shows `origWhen=+2m..` (about 2m45s to 3m left) |
| `files-new-folder` x2 in the first rerun | the agent saw `phonedriver` already listed and declined to make a duplicate (correct) | reset defect: deleting a folder with `rm` leaves its MediaStore row, so Files lists a ghost folder | the reset clears the media provider and Files' data, then waits 6 s |

No failure was caused by phonedriver (no wrong tap, missed element or misleading error). Agent behavior worth recording: in the Files rerun the agent refused to create a duplicate folder and asked the user, which is the right behavior for the state it was shown. `airplane-on-off` is the most expensive task (9 to 16 calls): Settings has several routes to the switch and the agent tried more than one; I did not analyze those transcripts further.

Open items found by the evaluation: a WebView checkbox shows no checked state in the snapshot (the agent verifies with a screenshot); the testbed's list rows give no visible feedback when tapped, so an agent cannot tell that Row 640 opened; `scroll --until` on the Compose list overshot Item 300 in 1 of 3 runs of a live test today (the `scroll` summary named the item, the next tap did not find it), the same family as the open M2 note. The 7.1 speed test (`a_frame_of_412_by_915_takes_under_120_ms_at_the_median`) failed once in the full test run while the machine was busy; it was not rerun.
