# M4: iOS Simulator scenarios and benchmark

Task 5.6, milestone M4. Everything below ran on the Mac mini, next to the simulator. Raw benchmark samples are in `docs/bench/data/m4-ios-run-{a,b}.csv`.

## Verdict

**M4 is met, with one stated deviation and one flake.**

- **Scenarios: 12 of 12, three runs in a row**, on the final code of the task (36 of 36). The same result held on the gate run before the last fixes and on nine recorded full runs in between. Before that, `settings-dark-appearance` failed twice in six full runs and its cause is not found; see "The flake" below.
- **D4: met on the same screens.** The runner's snapshot p50 is 2.04x to 2.08x faster than fully tuned WebDriverAgent on the List tab and Settings, and 2.06x on the Taps tab as task 5.3 measured it. WDA itself was not re-measured; see "D4" below.
- **Budgets (architecture 12, Runner / Simulator column): four of five met.** Snapshot, screenshot, type and tap to settled diff are met. Tap, request to delivered, misses: 357 ms against 80 ms. About 240 ms of that is XCTest confirming the synthesized event (decision D15).
- **Deviation:** the gate names the iOS 27 simulator. The mini has only the iOS 26.5 runtime and not enough disk for another (task 5.1), so M4 ran on iOS 26.5, built with the iOS 27 SDK.

### One-time preparation of the simulator

Each step was done by hand, once, and stays done on this simulator:

- **Keyboard:** dismissed the "slide to type" onboarding with Continue (on the iPhone 17 in task 5.5, on the iPhone 17e in this task).

## Scenarios

`phone-use-bench scenario --phone-use <binary> --device sim:<udid> --runs 3 bench/scenarios/ios/*.yaml`

Each scenario drives the real CLI (`--json`) step by step and checks one of three things:
- the CLI's replies;
- the simulator's own state (`simctl ui appearance`, the Files storage directory);
- the testbed's event log.

Every scenario leaves the device as it found it. Each one terminates its app, sets the appearance back to light, deletes the folder or contact it made, and so on. On a failure the runner keeps a screenshot and the snapshot text next to the daemon's traces.

### Three scenarios differ from the plan's list

The iOS 26.5 Simulator without an Apple Account cannot do them as written:
- **Reminders add:** Reminders has no local list. "New Reminder" and "Add List" stay disabled, and "Enable iCloud Syncing?" returns on every launch. Calendar's Add is disabled the same way. `files-new-folder` replaces it.
- **Settings search:** the search answers "No Results for …" for every query on this simulator ("Wi-Fi", "Camera"). The scenario checks that the query reached the field and that Settings answered for it. It cannot check that results appear.
- **Settings appearance to dark:** the Simulator's Settings has no Display & Brightness, so the scenario uses Developer > Dark Appearance.

### The flake

Before the final gate, `settings-dark-appearance` failed in run 3 of the first attempt and run 1 of the second: 2 failures in 6 full runs. It did not fail again in:
- 10 runs alone;
- 8 runs paired with `safari-open-url`, the scenario before it;
- 30 taps on the knob in a row (every one toggled);
- 9 full runs with the screen recorded;
- the 3-run gates before and after the last fixes.

In both failures, the trace shows a tap delivered at the knob (337,198) about 230 ms after the Developer page settled, the same timing as in passing runs. It settled in 383 to 389 ms, against 634 ms when it works, where the whole screen turns dark. The kept screenshot shows the switch off and the screen light. So something small changed and the switch did not toggle. The cause is not found; it is listed as unfinished in `progress.md`.

- The runner rows talk to the runner's socket directly, before the daemon starts.
- The other rows go through the daemon socket, as the Android benchmark does.
- Each op is timed from the request written to the reply read.

### What this task changed to get these numbers

The first runs (debug build, 50 runs) measured:
- tap 435 ms;
- snapshot 117 ms;
- screenshot 191 ms;
- type 444 ms, a miss.

Timing the runner directly showed a tap at 244 ms. The extra came from the daemon, which lists devices on every request: `simctl list` takes about 70 ms. `SimSource` now reuses a listing for 2 s. That took snapshot from 117 to 28 ms, screenshot from 191 to 83, tap from 435 to 357 and type from 444 to 355. Building in release changed nothing measurable (tap 434 ms).

## D4: runner against WebDriverAgent

D4's own reopen bar (WDA `/source` with `snapshotMaxDepth` tuned) is met by 8x to 19x, as in task 5.3. The project holds the runner to the stricter bar: WDA with every knob turned, where 5.3 measured 44.8 / 26.1 / 49.7 ms on the List tab, Taps tab and Settings.

WDA could not be re-measured in this task. Its checkout went with spike I4, and rebuilding it needs a download and about 1 GB of DerivedData on a mini with 2 GB free. The runner is therefore compared with 5.3's WDA numbers:

| Screen | WDA fully tuned p50 (5.3) | runner p50 run A | runner p50 run B | ratio |
|---|---|---|---|---|
| List (150 nodes) | 44.8 | 21.9 | 21.5 | 2.05x / 2.08x |
| Settings (168) | 49.7 | 24.1 | 24.4 | 2.06x / 2.04x |
| Taps as 5.3 measured it (59 nodes) | 26.1 | 12.6, 12.7, 12.7 (three 50-run series) | | 2.06x |
| Taps with the new Dark theme toggle (62 nodes) | (not measured) | 13.1 | 13.6 | 1.99x / 1.92x against the 59-node WDA number |

The Taps tab gained a toggle in this task, for the tap-to-settled-diff row, so it is no longer the screen WDA was measured on. To compare like with like, I installed the testbed as of the previous commit next to the new one. I alternated them three times, timing 50 runner snapshots each with the same client: 59 nodes measured 12.6 to 12.7 ms, 62 nodes 13.1 to 13.3 ms. The runner stays just over 2x on every screen WDA was measured on. The margin is still small, as 5.3 said: re-measure WDA after any Xcode update.

## Gaps seen while writing the scenarios (not fixed in this task)

- **Hidden content:** content under an overlay stays in the snapshot. With Settings search open, the root list behind the results is still listed.
- **Repeated values:** web texts repeat their label as their value (`text "Example Domain" "Example Domain"`), and every text in a web page is marked `focused`.
- **Slow swipe settle:** `swipe up` on the List tab settles in about 2.6 s. A half-screen drag moves the list about 20 rows (880 pt), so the list keeps moving after the lift despite the 100 ms hold.
- **Waiting behind polls:** every request waits for an in-flight settle poll (up to 80 ms), which is most of the p95 above.
- **Leftover noise from 5.5:** unlabeled `cell` wrapper lines, two "Dictate" buttons in search fields, and cells whose refs move by closest bounds.

## launch, open and swipe

The scenarios need `launch`, `open` and `swipe`, which belong to Android Phase 3 and were not merged when this task ran. This task added minimal versions:
- **CLI:** the verbs in `commands.rs`.
- **Wire:** `Action::Swipe`, `Action::Launch`, `OpenParams` in `wire.rs`.
- **Actor:** their arms in `actor.rs`, the `open` route in `daemon/mod.rs`, and `daemon/gestures.rs`.

They are meant to be replaced by Phase 3's versions at the merge, keeping the iOS scenarios passing.
